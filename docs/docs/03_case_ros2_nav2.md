# 03 案例：ROS2 / Nav2 工程学习

## 背景

这个案例记录了我在 2026 年 1 月到 3 月初，围绕 ROS2、Nav2 和机器人导航工程能力进行的集中学习过程。

这段学习不是以课程为中心，而是以真实工程项目为中心。

目标不是“学完 ROS2”，而是建立可以被验证、可以被复盘、可以被展示的机器人软件工程能力。

## 时间线

| 时间 | 阶段 | 内容 |
|---|---|---|
| 2026-01-04 到 2026-01-11 | 环境搭建期 | 安装 ROS2，跑通 TurtleBot3 / Nav2 基础链路 |
| 2026-01 中旬到 2026-02 底 | 工程学习期 | Nav2 参数实验、评估脚本、runbook、debug 文档、阶段总结 |
| 2026-03 初到 2026-03-12 | 求职转化期 | 整理项目表达、准备面试问题、形成工程能力证据链 |

## 学习方式

我没有采用“先系统看完课程，再开始做项目”的方式。

实际流程是：

    先进入真实工程问题
      ↓
    遇到问题后使用 AI 辅助拆解
      ↓
    通过命令、日志、代码和实验验证结果
      ↓
    阶段结束后写 docs
      ↓
    通过问答检查自己是否真正理解
      ↓
    最后整理成 GitHub 作品集和面试材料

## 关键实践

### 1. 跑通基础链路

第一阶段重点不是深入优化，而是先让系统跑起来。

包括：

- ROS2 Humble 环境安装
- TurtleBot3 Gazebo 仿真启动
- Nav2 bringup
- RViz 设定初始位姿
- 发送导航目标
- 确认 map、tf、odom、cmd_vel 等基础链路正常

### 2. 建立工程调试习惯

学习过程中重点记录：

- 启动命令
- 报错信息
- 修复步骤
- 参数修改
- 验证命令
- 成功标准

这让每一次调试都不只是“解决一次问题”，而是沉淀成以后可以复用的工程文档。

### 3. 阶段计划控制学习范围

AI 可以快速推进任务，但也容易发散。

所以每个阶段都要限定目标，例如：

- 只跑通一个 demo
- 只理解一个 Nav2 节点
- 只修改两个参数做对照
- 只写一个 debug report
- 只准备一组面试问答

这样可以避免学习过程失控。

### 4. 文档复盘

每个阶段结束后，把学习结果写成文档。

典型文档包括：

- README
- runbook
- weekly summary
- debug report
- experiment notes
- interview Q&A

文档的作用不是装饰项目，而是把学习过程变成可以复习、可以展示、可以验证的资产。

## 方法价值

通过这个过程，我获得的不只是 ROS2 / Nav2 的知识，而是一套工程学习闭环：

    做过
      ↓
    记录过
      ↓
    复盘过
      ↓
    讲得出
      ↓
    展示得出

这也是工程作品集驱动学习法的核心价值。
